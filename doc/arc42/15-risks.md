# 15. Risks and Technical Risks

> *Risk register: what could go wrong, impact, likelihood, mitigation/contingency.*

| ID | Risk description | Impact (H/M/L) | Likelihood (H/M/L) | Mitigation / contingency | Owner |
|----|------------------|----------------|--------------------|--------------------------|-------|
| R1 | Web bundle size exceeds the proposed P3 budget (2 MB): S-019 measured JS+wasm = 13,137,832 B ≈ 12.5 MiB **uncompressed and unoptimized** (`wasm-opt` skipped — sandbox egress blocks the binaryen download; `data-wasm-opt="0"` in `gui-app/index.html`). Optimized size still unknown until measured where github.com is reachable. | M (P3 is "awaiting confirmation", not a gate — but 12+ MiB of wasm is slow to download/compile on constrained networks/devices) | H (already over budget before optimization is even applied) | Re-measure with `wasm-opt` enabled (drop the attribute); if still over budget, revisit P3 in §5.3/§14 — options: lazy-load wgpu/renderer init, trim eframe features, or raise the budget with a recorded rationale | Next release prep / S-021 doc pass |
| R2 | `gui-app` does not compile for `wasm32-wasip1`: eframe → wgpu 30 pulls `wgpu-hal`'s gles backend, which fails under WASI p1's no-threads model (E0277, `RefCell<BufferMapState>` not `Sync`). Discovered during S-020 when the bench targets were added to the wasip1 gate. | M — wasm test coverage is limited to the five core crates (`wasm32-wasip1`); the actual web target (`wasm32-unknown-unknown` + WebGL) compiles and runs fine, so shipping is unaffected | H (observed on current wgpu; pre-existing, not caused by S-020) | Keep `wasm32-wasip1` as a *core-only* test target (documented in S-019 AC5 + S-020); track upstream wgpu WASI support; do not gate releases on it | Maintainer |
| R3 | Performance budgets are unconfirmed: P1 (< 100 ms first render at the 200×100-cell envelope) is "proposed, pending confirmation" (§5.3). S-020 measured the baseline (500 objects ≈ 409.6 µs — ≈ 240× under P1; export scaling text sub-linear, SVG/PNG ≈ linear), but a future stakeholder-confirmed budget could be stricter than the envelope assumed. | L (current headroom is ~2 orders of magnitude) | M (budgets explicitly await confirmation) | Budgets recorded as measured-baseline + proposed in [§6](06-quality-model.md); criterion benches re-runnable per change; if the envelope grows beyond 200×100 cells, re-measure before confirming | Maintainer / stakeholder |
| R4 | egui/eframe API churn: platform semantics changed between versions and bit us — winit's X11 pointer-grab stacking required a one-shot `StartDrag` per gesture (B-004), and egui 0.37 made `PointerState::button_pressed` edge-triggered (held state = `button_down`). A future upgrade can silently regress window controls or gesture handling. | M — window chrome/resize is user-visible core UX | M (egui is pre-1.0; breaking changes have happened twice already) | Pin the eframe version in `Cargo.lock`; tier-0b regression tests cover drag/close/resize gestures headlessly; golden images re-diffed on any GUI dependency bump; ADR 017 v3 documents the client-side resize gesture contract | Maintainer |
| R5 | Heavy property/determinism tests vs tarpaulin's per-binary timeout: a 500-object determinism pass takes ≈ 26.6 s in debug builds — over tarpaulin's 30 s per-binary budget and flaky under load. | L — coverage runs fail intermittently, not product behavior | M (debug-mode slowness is structural) | S-020 split the scales: CI-scale determinism at 50 objects (≈ 0.75 s), the 500-object envelope lives in criterion benches (release builds) only; keep new heavy tests off the tarpaulin path or scale them down | Maintainer |
