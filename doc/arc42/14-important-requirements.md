# 14. Identification of Important Requirements

> *The subset of functional and non-functional requirements that the architecture must satisfy — traceable to quality goals.*
>
> *arc42 convention: this section is a **selection**, not the complete requirements catalog. The full set of requirements is managed in: [TBD — e.g. separate spec doc, issue tracker]. Only architecturally relevant requirements are listed here.*

## 14.1 Functional Requirements

| ID | Requirement | Source (feature/user) | Priority |
|----|-------------|------------------------|----------|
| FR1 | User can place, move, and resize predefined shapes (boxes, circles, …) on a canvas | §1.1 Obj. 1 | High |
| FR2 | Diagram is exported as plain monospace text (svgbob-compatible ASCII per [ADR 001](../adr/001-glyph-resolution-alphabet.md)), copy/paste-able anywhere: terminals, READMEs, chat, docs — and directly parseable by svgbob tooling; the text output can be written to a `.txt` file via Save As in addition to clipboard copy | §1.1 Obj. 2, CR-001 | High |
| FR3 | Users can define their own diagram objects entirely (custom geometry/glyphs beyond the predefined set) and store them in named collections for grouping and reuse across diagrams; custom objects can declare resize behavior — per-edge character insertion/removal rules for growing/shrinking, plus optional parity variants (alternate patterns for even/odd sizes) so curved shapes stay correct at every size | §1.1 Obj. 3, customer requirement, CR-003 | High |
| FR4 | Diagrams are saved to and loaded from the open plain-text file format via system file dialogs — Open / Save / Save As (round-trip: reload → identical model); Save As additionally offers writing the rendered text output as `.txt` instead of the diagram document | §1 Background (open format), CR-001 | High |
| FR5 | Diagrams export as SVG (vector) and PNG (raster) in addition to text, chosen in a single Export dialog where the user selects the target format; vector output is derived from the resolved character grid via svgbob ([ADR 005](../adr/005-use-svgbob-as-vector-renderer.md)), so exports always match the text representation exactly | §1.1 Obj. 5, rendering model: svgbob (§1 Background), CR-001 | Medium |
| FR6 | UI consists of a top menu bar with dropdown menus that group actions by category (e.g. File), a template sidebar with a filter input that narrows the shape list by name, and an editor canvas, plus an optional right-side preview pane showing the diagram's rendered SVG — resizable by dragging its border, hideable, and re-opened via a “Preview” bookmark at the right edge of the window (minimal); groups in the menu bar and in the sidebar are collapsible and can be organized into subcategories | §1.1 Obj. 6, CR-002/CR-004/CR-011/CR-012 | High |
| FR7 | Shapes align to the cell grid | §1.1 Obj. 7 | High |
| FR8 | A scale control scales the entire diagram's rendered output up (larger spacing → more readable text output), not just a display zoom | §1.1 Obj. 7 | Medium |
| FR9 | Connectors (lines/arrows) can be drawn between/around shapes or standalone with freely positioned ends; each end is either bound to a shape anchor — staying attached when the bound shape moves or resizes — or free at an explicit position, and ends can be attached to and detached from anchors interactively; the user can modify a connector's shape — pressing onto it selects it, and dragging adds/moves intermediate bends (waypoints) so arrows can be routed manually for readability; connectors without manual bends keep the automatic routing; each end of a connector can carry a selectable tip style — no tip, hollow arrow, empty rhombus, filled rhombus — changed by pressing onto the tip; connection points are shown in the GUI as small arrow symbols to indicate that connecting adds an arrow | Usage reference: asciilogic (§1 Background), CR-007/CR-008/CR-010 | Medium |
| FR10 | Free text can be placed as an element on the canvas (independent of shapes) | Usage reference: asciilogic (§1 Background) | Low |
| FR11 | Every object type exposes anchor points for connectors (FR9), **per type** — the anchor set is part of the shape definition and shared by all instances: user-defined shape templates declare their own anchor cells, definable both textually in the template file and graphically in a template editor ([ADR 007 v2](../adr/007-user-defined-diagram-objects.md)); predefined shapes ship with standard default anchors (basic positions + official UML connection points); imported/registered shapes receive anchors when registered (FR12). The exact default anchor set per predefined shape is an open spec point | §3.2 F2, Q3 (product interview 2026-10-18) | Medium |
| FR12 | Existing ASCII diagrams can be imported: regions matching known shape templates load as fully editable objects; unknown regions load with a warning in reduced form (fixed-size, no grouping) until they are optionally registered as new custom shapes — registration declares anchor points and resize behavior, which makes the shape fully editable (**v1+**, not in v1 scope) | §3.2 F9 (product interview 2026-10-18) | Medium |
| FR13 | The application provides an Options menu where user preferences can be modified; the UI theme is selectable — light (mainly white), dark (mainly dark), native (inherited from the system/window manager, default) — and the selection persists across sessions in the application's config file | CR-005 | Low |
| FR14 | The GUI is styled according to Material Design (color system, typography, elevation); on native targets the window border is a custom Material app bar with minimize, fullscreen and close controls — the editor canvas keeps its monospace rendering so the ASCII art stays WYSIWYG | CR-006 | Medium |
| FR15 | A diagram can have a background color, a shape fill color and a line/text color, chosen with a color picker that remembers the last 16 used colors; the colors are stored with the diagram and shown on the canvas and in SVG/PNG exports (via svgbob `Settings`) | CR-009 | Medium |
| FR16 | Shapes in the template sidebar are shown as pre-rendered previews of their glyph pattern, generated from the same pattern bytes the renderer stamps on placement — what the user sees when picking a shape is exactly what gets placed (WYSIWYG). Previews stay legible for templates of any size within the sidebar width | CR-013 | Medium |
| FR17 | The user can pan the canvas to navigate a diagram that extends beyond the visible area. Panning only changes which part of the model space is displayed; it never changes the diagram model or its rendering, and all canvas gestures keep working at any pan offset | CR-014 | High |
| FR18 | The predefined catalog covers the core UML shape set for the standard diagram types (class, use case, sequence, component, deployment, state machine, activity): at minimum interface lollipop, actor, activation bar, component, port, deployment node, artifact, rounded-rectangle state, decision diamond, initial and final state nodes — in addition to the existing box and ellipse. Every new shape is a built-in with standard anchors (FR11); shapes carry geometry only, UML semantics come from shape-owned text boxes (FR19) and free text (FR10). The exact glyph art and per-shape anchor sets are finalized in the implementing story | CR-015 | High |
| FR19 | Shape templates can declare one or more named text regions (text boxes) with a position and extent within the shape. Instances carry per-region content, and regions move and resize together with the shape. Regions are definable both textually in the template file and graphically in the template editor (mirroring anchors, FR11). The existing single shape label remains supported | CR-016 | High |
| FR20 | Multiple objects can be selected simultaneously in the GUI by Ctrl- or Shift-clicking them, and the whole selection can be moved as a group: dragging any selected member moves every member by the same delta. Delete removes every selected object together with its connectors; Escape clears the selection | CR-017 | Medium |
| FR21 | The resize handle of the selected shape is drawn with a dedicated resize symbol that is visually distinct from anchor dots and clearly conveys drag-to-resize. The exact glyph and color are specified in the implementing story | CR-018 | Low |

## 14.2 Non-functional Requirements

| ID | Requirement | Quality goal ref | Priority |
|----|-------------|------------------|----------|
| NFR1 | One codebase runs on Windows, macOS, Linux **and** in the browser (WASM) | [Q2](01-introduction-and-context.md#12-quality-goals-top-level) portability | High |
| NFR2 | File format is open and human-readable **without any renderer** (plain text) | [Q3](01-introduction-and-context.md#12-quality-goals-top-level) openness/readability | High |
| NFR3 | No automatic layout rearrangement — element positions are exactly where the user placed them; rendering is a **pure deterministic function** of the diagram model (no randomness, no external state); same model → byte-identical output | [Q1](01-introduction-and-context.md#12-quality-goals-top-level) determinism | High |
| NFR4 | Low learning curve / minimal UI complexity: a new user can compose a first diagram without documentation | [Q4](01-introduction-and-context.md#12-quality-goals-top-level) usability | Medium |
| NFR5 | Rendering/export core is platform-independent (shared crate) and unit-testable headlessly, with ≥80% coverage | [Q5](01-introduction-and-context.md#12-quality-goals-top-level) testability | Medium |

> *Notes: FR3's user-defined objects and collections are specified by [ADR 007](../adr/007-user-defined-diagram-objects.md) (proposed). NFR3 is the architectural answer to the PlantUML "spaghetti" problem (see §1 Background). Testable properties — NFR2: opening the file in any text editor shows the diagram; NFR3: rendering the same model twice yields byte-identical text. Quality goals defined in [§1.2](01-introduction-and-context.md#12-quality-goals-top-level); measurable scenarios and test strategy defined in [§6](06-quality-model.md). FR4's file format: see [ADR 004](../adr/004-diagram-file-format.md) (proposed). FR9/FR10 derive from the asciilogic usage reference (§1 Background); FR9's connector statements feed ADR 004's open spec points. NFR3 + ADR 001 together make rendering a deterministic glyph lookup — no layout engine, no randomness. FR11/FR12 derive from the business-scope interview ([§3](03-business-scope.md), 2026-10-18); FR12 is explicitly scoped to v1+. FR5: SVG/PNG share the resolved character grid with the text output — one deterministic pipeline (see concept C2, [render-pipeline](12-concepts/render-pipeline.md)); vector interpretation is delegated to svgbob directly on the canonical grid (ADR 005, ADR 001); the grid is a derived intermediate, not the storage format (ADR 004). FR13–FR21 were added by the bulk acceptance of CR-001…CR-018 on 2026-10-31 (`doc/crs/`); FR2/FR3/FR4/FR5/FR6/FR9 were extended by the same change — each CR file records its own requirement wording and decision.*
